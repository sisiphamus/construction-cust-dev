# Engineer A (small Texas civil engineering firm partner) - built an internal ops system with an AI coding assistant

## Summary

The engineer walked through an internal operations system he built to run the firm. Interviewer 1 showed his own setup in return.

## Main themes

- **Build for buy-in.** Philosophy: do something once, fine; twice, find a better way; never a third time slow. He takes almost every team suggestion (even dark mode) because once someone's idea ships they take ownership and start "dreaming about" the system. Never shoot down suggestions or people go into a shell.
- **From workflow automation to an AI coding assistant.** For about seven years the firm's automations ran on Microsoft Power Automate (email parsing, job-number matching, filing). His "aha" was a 25-minute AI-coding-assistant session that printed, renamed and reordered 500 invoice emails to PDF, including a Python script so it would not burn tokens. He now runs a unified internal ops system.
- **The buried-spreadsheet wedge.** "The value in all of this is that spreadsheet that's buried somewhere that only one person knows about. You go automate that, now you got something." Echoed by a friend's example of a materials-pipeline automation that drove 30% more profit in a quarter by solving one person's job.
- **Every company's ops are bespoke, so generic SaaS fails.** Over ~10 years he has tried Monday.com, Jira-like tools and others; none tracked the granularity he wants (down to "take out the trash"), which he insists on so the team feels their work matters. He doubts a one-size tool can be sold unless you listen inside a company for a month first.
- **Biggest internal sticking point:** the invoicing workbench is too complex to simplify and one accounts-receivable person is the bottleneck. Old tools were duct tape that only he could fix. Building real custom software used to cost thousands and more.
- **Vertical integration / own the data layer.** When Interviewer 1 described wanting to sit on top of point tools (lead gen, inbox cleanup, AI-search optimization) and package them for average users, the engineer pushed back toward owning the data-entry layer: if you build the system people already type into, you own the metadata of every transaction (loyalty-card analogy) and can match demand to supply across the trades. "It's really the metadata of that transaction that's valuable... do that for construction."
- **Voice / podcast shift.** He built a feature that auto-writes a daily project brief (a few cents) and converts it to an audio "podcast" he listens to each morning (about 17-20 cents). He thinks it could be sold but is only as good as the data fed in.
- **Generational build instinct.** Stakes are low while young; the only way to learn is by doing; most good ideas come out of conversations.
- **Interviewer 1's pitch context:** "No matter what happens with AI, people want more customers. That's not going to change."

## Quotes

- "If you do something once, I'm fine. If I do something twice, I'm finding a better way to do it. But I'm not doing it a third time slow."
- (Close) "One day you need to come to our old man breakfast and you could nerd out with us... we talk AI and yell at each other. It's great."

## Buy signal

None. Warm relationship and an advisor-type contact.
